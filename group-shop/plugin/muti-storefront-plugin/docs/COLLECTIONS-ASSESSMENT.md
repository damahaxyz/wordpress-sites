# 商品集合评估（2026-11-05，0.5.4历史评估）

后续0.5.5按用户新授权已实施原生分类共享／店铺视图和集合parent层级，补齐新建集合品牌标记及显式选品归属检查；下文记录此前评估背景，当前行为以README／HANDOFF为准。尚未迁移taxonomy或移动中央集合标签。

建议保留“共享分类＋品牌集合”两种职责。原生分类管理商品目录结构；集合管理各品牌的首页推荐、活动选品和独立排序。当前用户的一套商城、多品牌门面、共享公共商品模型，适合复用分类作为集合选品条件，而不是把集合直接变成共享普通分类。

| 维度 | 共享商品分类 | 品牌商品集合 |
|---|---|---|
| 范围 | 公共商品统一维护，品牌版本继承 | 每个品牌自己的销售版本 |
| 用途 | 长期目录、层级、浏览入口 | 首页精选、主题页面、活动选品 |
| 成员 | 原生分类归属 | 分类／标签条件，加手选、排除 |
| 排序 | 普通商品排序 | 集合各自置顶与排序 |
| 数据 | 原生product_cat及关系 | 原生词条／关系＋品牌集合规则 |

假设公共商品P同时在A、B销售：P的共享分类应一致；A可以把A版本放进“首页精选”，B可以选择其他商品或不同顺序。公共内容继承不应把A的营销选品同步到B。当前ProductVersions::parent_fields会继承普通分类，同时保留所属品牌的集合关系，已经体现这一区分。

目前集合不是第二套商品库。Collections::save_collection在原生product_cat创建带_gsm_collection标记的词条，规则保存在品牌gsm_collections option；reconcile把匹配结果写成原生分类关系。CollectionDisplay以同一份成员提供动态区块、短代码、专题和经典Shop筛选；前台查询仅发布商品。

原生分类标准界面能维护名称、层级、描述等词条资料，但不能直接维护本插件的规则组合、手选／排除／置顶、品牌独立启用和集合展示选项。若全塞进分类编辑页，仍需重建这些集合表单，并容易与全站共享分类的继承规则混淆。若实际只需要固定共享分类商品展示，无品牌选品和独立排序需求，则可以直接用分类条件展示，没必要为了每个分类再创建集合。

建议后续改造方向：

1. 保留独立集合管理职责，统一放到Products → 商品集合会更容易理解；本轮尚未移动入口。
2. 原生Categories专注共享目录，集合不再承担商品内容、价格或发布管理，编辑商品统一跳原生Products。
3. 集合选品始终使用当前品牌销售版本，公共商品和其他品牌商品不能成为成员；分类和标签只作为共享条件。
4. UI优先展示手动选品／按分类标签自动选品、置顶／排除及排序，其他展示选项收进高级设置。
5. 底层继续复用WordPress词条、媒体与关系，短期保留既有ID／页面和区块引用。当前集合借用product_cat会与普通分类同处一个词表，后续应明确区分编辑入口，避免普通分类编辑绕过集合规则；是否迁到独立taxonomy应另行评估兼容和迁移成本，不在本轮自动执行。

静态检查另发现一个应优先验证的实现问题：SingleMigration为迁移的私有集合写入_gsm_brand_id，但Collections::save_collection的新建路径只写_gsm_collection／图片／顺序，未见同样的品牌归属写入；BrandScope和ProductVersions又依赖这个标记过滤集合关系。新建集合的归属写入与后续过滤存在不一致，后续应先做新建集合验收并修复，避免成员关系被剔除。这是现有实现的检查发现，不改变集合应独立管理的职责判断；本轮没有创建集合验证运行结果。

当前同步重建有每品牌2000父商品限制，集合上限50，手选／排除／置顶各200；规模超过时再改异步更新，不应为了改入口就重新实现存储或全量迁移。规则目前只支持分类、标签与显式商品，不把按日期排序等同自动“新品”条件，也不把人工热卖推荐等同销量规则。

本轮仅阅读现有实现并给出方案，没有修改集合规则、数据、前台模块或存储。源：includes/class-collections.php、class-collection-display.php、class-product-versions.php、class-taxonomy-admin.php。
