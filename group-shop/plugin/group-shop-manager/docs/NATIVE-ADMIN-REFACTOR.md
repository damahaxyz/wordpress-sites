# 原生后台复用与主题差异数据：逐项分析

日期：2026-11-03（Asia/Taipei）。**整体重构仍为设计分析。** 初次分析时线上为 0.2.0，只更新本地文档。后续 0.2.1 按用户逐项开发要求，仅先实施店铺 Logo 原生媒体选择及搜索引擎收录设置；本文其他界面收缩尚未实施。实际上线版本以 HANDOFF 为准。

## 2026-11-04 用户身份实施（0.4.0，本地）

最新用户需求覆盖旧共享顾客方案：顾客按店独立原生 ID、可见用户名和真实邮箱可跨店重复，密码／地址／会话独立；员工独立共享身份按店授权，顾客固定 Customer，不转员工。仍用原生网络／各店用户列表与资料编辑器，补类型／范围、别名、只读归属和员工逐店授权，不恢复共享客户标签。原生网络新增用户用于员工；前台注册用于本店顾客。身份解析、权限、Cookie、重置、REST、隐私工具及显式迁移由插件负责，具体当前边界见 ARCHITECTURE／HANDOFF。下文 0.3.6 的“共享资料保留、只补来源、无用户迁移”为历史版本，不再适用于 0.4.0。

## 2026-11-04 主商品发布退休（0.3.7，本地）

用户明确移除“主商品发布”标签及功能，而非移动到原生面板。跨店复制、字段覆盖、变体复制、媒体导入和新映射写入 API 全部删除；旧地址回概览、旧请求拒绝，无替代发布入口。保留已存在商品／变体／附件和旧映射，后者仅继续用于既有分类／标签归属同步。Catalog 只剩本店编辑／上下架，不改其校验。下文将发布移动到原生批量操作／面板的建议已撤销，不得按历史规划恢复。证据及只本地状态见 HANDOFF。

## 2026-11-04 用户实施状态（0.3.6，本地）

已移除“共享客户”标签及重复全网列表，概览入口改到原生网络用户管理。只增加只读首次来源店铺列，使用现有 _gsm_first_store；Sites 原成员关系列复用，不把历史访问混为当前成员。无用户／地址迁移，无新元数据或写操作；Customers 登录、角色关联、密码范围提示与会话失效仍保留。各店用户列表和 Woo 消费统计／游客客户保持原生范围。当前这三类重复列表已收缩，但商品／店铺等其余界面仍按需求规划，未称整体完成。实际验证与未上线状态见 HANDOFF。

## 2026-11-04 评论实施状态（0.3.5，本地）

已按用户要求移除“独立评论”标签、自建列表／审核表单和专用处理器。所属店原生 Products → Reviews 增加一列“所属店铺”，评论及回复按当前 blog_id 显示店名与编号；不加 commentmeta、不迁移评论、不聚合全网。原生审核、编辑、回复、筛选、批量操作与第三方列保持，权限不变。普通 WordPress 评论列表不扩展。旧标签回概览、旧写请求拒绝。仅本地完成，客户等其他后台收缩仍待后续需求，实际验证见 HANDOFF。

## 2026-11-04 订单实施状态（0.3.4，本地）

用户确认直接使用原生订单管理，移除中央“统一订单”标签、自建列表／详情和备注／状态处理器。概览保留按店原生入口，目标店内判定 HPOS／传统存储。来源快照、前台归属保护及已有 HPOS 来源列保持。取消跨店同屏汇总，不另做跨店原生查询适配；独立域名分别登录，原生能力／通知／网关规则接管操作。下文涉及中央订单重构的建议已由本节替代，客户／评论等整体收缩仍为规划。真实验证与环境变更见 HANDOFF。

## 2026-11-04 集合实施状态（0.3.2，本地）

按用户明确将集合设为核心选品功能的方向，已实现列表／独立创建编辑／可恢复回收站，保留标题、描述、媒体封面，无 slug／父级输入；分类、标签及搜索手选组合。增加原生页面“商品集合”动态区块、短代码与主题读取约定，经典 Shop 集合筛选与原生属性／价格叠加。集合身份与成员保持跨主题持久、本店归属，已有原生关系和 URL 兼容。不是整体后台收缩完成，也不自动替换主题写死模块。Store API 独立查询仍需要相应适配。最新验证与未发布状态见 HANDOFF。

## 2026-11-03 最新覆盖决定（0.3.1）

最新用户明确要求全店共用唯一分类／标签数据：只在主站原生 Products → Categories／Tags 维护，修改全店生效。此决定覆盖 0.3.0 独立分类方向。SharedTaxonomies 在主站原生权威与分店 Woo 原生投影之间协调，没有旧模板／继承／覆盖 UI。主商品分类归属同步到关联版本；集合按店独立。

0.3.1 已按本轮要求改善中央店铺商品操作：主图列表、独立上架／草稿禁用、移除库存列与分类编辑、原生富文本／本店媒体、每页 20 个变体同页及本页批量填价；修复 Code 工具按钮宽度与富文本插图别名请求上下文。仍保留此中央编辑页，不把原生商品／订单／客户／评论整体收缩写成已完成。店铺列表与弹窗继续保留。所有代码与数据测试仅本地，需新通知才上线，实际状态见 HANDOFF。

下文早期分析中“各店分类独立”“不关联分类／标签”的内容已被本节覆盖，其余未实施建议仍为规划。

## 用户已确认的方向

能使用 WordPress / WooCommerce 原生后台处理的功能，尽量直接使用原生页面，通过字段、列表列、筛选、批量操作或编辑面板扩展。插件重点是不同店铺供不同主题读取的差异数据、跨店映射和必要协调能力。

差异以店铺 ID 为归属。主题负责展示，切换主题应保留店铺品牌、商品内容、价格、评论和订单。当前 Multisite 与原生店铺数据不重建；用户身份已由 0.4.0 新决定更新，仍保留无限库存、支付待定等决定。

## 多主题真正需要的数据

### 原生字段继续作为权威来源

- 站点名称、说明、域名、Logo、站点图标：使用 WordPress 原有字段和适用主题的设置界面。
- 商品名称、详情、短描述、售价、促销、主图、相册、变体、分类、标签、发布状态：使用该店原生 WooCommerce 商品。
- 分类名称、别名、说明、封面、父级：使用该店原生分类字段，各店独立维护。
- 页面、文章、菜单、导航、媒体、替代文字：使用原生编辑器和媒体选择器。

商品名称、价格、图片等应同时提供给主题、购物车、结账、订单、邮件、公开 API 和结构化数据。不要把真实商品差异仅留在某个主题的输出替换中。现有每店原生商品版本可以继续使用，不为界面重构再建立另一份商品业务库。

### 插件应新增或统一约定的内容

- 历史主商品与各店商品／变体来源保留作兼容，0.3.7 已取消新发布、字段覆盖和复制；既有映射分类／标签归属同步按 0.3.1 决策保持。
- 原生没有对应字段的品牌内容，例如品牌故事、首页横幅、场景图、卖点、FAQ、服务承诺、尺寸说明等；按实际主题需要确定字段，不先做全能装修器。
- 主题使用统一的数据读取约定，通用品牌内容不绑定主题文件；主题专属布局/颜色/位置等继续放该主题的原生配置中。
- 经典主题的一些设置保存在 theme_mods，不能假定原生 Logo/装修字段天然跨主题保留。需要时通过店铺级品牌引用和原生字段映射衔接，仍使用原生选择界面并明确唯一来源；主题专属尺寸图片/模块配置可按店铺+主题保存，商品价格等经营数据始终归店铺。
- 首页选品来源、持久集合和默认排序，只补原生区块/查询不能直接表达且业务确实需要的部分。
- 更换主题后的缺失字段提示或适配清单，不自动覆盖店铺经营数据。

## 分类与集合的具体收缩

原生分类编辑器已经提供名称、别名、描述、父级、图片等，不再复制这些表单。按最新决定，各店原生分类完全独立，不再提供模板或继承/覆盖。原生保存、删除、批量操作都要接入映射/集合逻辑，不能只把菜单改成跳转后遗漏数据一致性。

Woo Product Collection 已支持分类、标签、手选及多种筛选，页面上的基础商品陈列应优先使用它。只有需要跨主题保存一套集合身份/规则、额外组合语义或稳定归档关系时，才保留相应规则和原生分类物化。0.2.0 的集合不能未经盘点直接删除：它们可能已经用于链接、菜单、页面或 SEO 归档，需要迁移兼容。

0.3.0 删除模板来源/覆盖元数据，但保留已经存在的分店名称、图文、排序、附件和基本商品归属；集合条件先转换成本店编号，不能直接丢弃映射。以后不规划模板传播。

## 原生后台与跨店统一管理的边界

当前 Multisite 中，商品、订单、评论等按店分表，原生列表默认查询当前站点。在原生页面增加店铺下拉框，可以切换查看某个店；同时列出全部店的数据还需要聚合查询和正确的操作归属。UI 复用不等于原生查询自动具有跨店能力。

原生完整处理应在订单/评论/商品所属店上下文执行，并使用该店的权限、邮件与插件流程。跨店对象要保留“店铺 + 本地编号”的身份，避免两个店相同编号混淆。不要把订单复制到主店来实现列表统一。

推荐优先复用原生单店处理，同时提供统一入口及必要跨店总览。若要求所有编辑都始终留在主域名，需要专门的后台店铺上下文适配；不能只通过一个 URL 参数切换表前缀或直接套用原生表格。具体交互需在实施设计时明确，不表示取消用户原有统一处理要求。

现有不同域名分别登录的范围保留；复用所属店后台可能触发该域名登录。自动 SSO 尚未实现，不能把页面跳转描述成已经无感共享登录。

共享账户管理与 Woo 客户消费报表也应分开理解：前者是原生网络用户，后者来自店铺交易，包含游客客户。不要把游客记录强行变成共享注册账号，或把某店消费统计当成全网络统计。

## 其他相关功能

- **库存**：继续全网络不管理数量、始终有货，保留策略与迁移，不恢复库存页面；原生编辑器相应字段应说明实际策略。
- **邮件**：模板、通知、发件设置优先复用 Woo；传输仍用 FluentSMTP。插件保留原始店铺上下文、精确发件路由、配置状态及发送保护；避免自定义配置和原生设置各存一份互相覆盖。禁止顺带修改 FluentSMTP 核心。
- **媒体**：恢复原生上传、预览、主图/相册选择器，去掉人工附件编号操作。跨店导入与来源映射仍是必要插件逻辑，附件编号不能跨店直接复用。
- **SEO**：复用原生/已有 SEO 集成的页面和字段，保证标题、链接、图片与结构化数据使用一致的本店真实数据；不另做 SEO 后台、不承诺搜索引擎无法识别品牌关联。
- **权限**：新增字段/筛选不扩大跨店访问权限；网络管理员才可执行跨店管理，原生店铺权限保持。共享账户不等于顾客可看其他店的订单或评论。
- **支付与退款**：继续待定，未来复用原生网关和订单流程；本次分析不启用新支付/退款能力。
- **缓存/部署/监控**：保留已有安全门禁和运维，不为经营后台重新实现部署系统。新读取字段参与现有缓存失效，避免编辑后旧主题数据继续显示。

## 推荐的重构顺序（规划）

1. 将商品、媒体、分类、评论和客户的基础编辑接回原生页面，加入必要来源/继承字段。
2. 主商品发布已于 0.3.7 按用户要求彻底退休，不再移至原生批量操作或编辑面板。
3. 定义店铺切换、跨店总览和原生完整处理的交互；再收缩自建订单界面。
4. 盘点主题实际需要的差异字段；通用数据归店铺，布局归主题，常规选品优先用原生区块。
5. 迁移既有集合入口/菜单/规则并验证 native editor、批量操作、媒体上传、API、前台及邮件一致性，最后删除旧界面。

不重建业务数据、不改变当前主题或域名、不把本分析标记为已开发。下一轮实施时应先读本文件、当前 HANDOFF 和原生编辑钩子，再按功能分批验证。
